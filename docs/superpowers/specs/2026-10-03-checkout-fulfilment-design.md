# Checkout and fulfilment — design

Date: 3 October 2026 · Status: approved in conversation · Scope: Build 5 of NEXUS

## Goal

Turn the prototype into a shop that takes money and delivers: a customer pays through Stripe's hosted checkout, the order is placed and paid with CJdropshipping automatically, the customer can see where it is and gets a shipping email with tracking, and Nick sees every order and every problem in one place. Nothing about this adds a monthly bill: the back office is a Cloudflare Worker on the free tier, deployed from the same repository.

Success looks like: a test-mode purchase on the GitHub Pages site ends on a confirmation page showing a real order number; within a minute the order exists in CJ's system; the merchant view lists it; when CJ marks it shipped the order page shows the tracking number and the customer's shipping email has gone out; and a deliberately broken order (empty CJ wallet) shows up as "needs attention" with an email to Nick instead of silently failing.

## Decisions already taken (from the conversation)

- Only products with a supplier (Radar listings, `product.supplier`) can be bought at launch. The 64 branded products stay visible for discovery with a "Not yet stocked, tell me when" button.
- Returns: 30-day change of mind on Australian-stocked items only, at the customer's postage cost; faulty-goods rights under Australian Consumer Law on everything; no change-of-mind returns on items shipped from China.
- Nick will buy a domain; order and shipping emails are built in and switch on when the domain is verified. Until then Stripe's receipt is the only email.
- No ABN yet: everything is built and tested against Stripe test mode; going live is a key swap.
- Back office: a Cloudflare Worker with KV, not Shopify, not a second private repository.

## Non-goals

- No accounts or logins for customers; order lookup is by order number and email.
- No stock synchronisation with CJ before checkout; a stock problem surfaces at fulfilment as "needs attention" and is refunded by hand in Stripe.
- No multi-currency charging: Stripe charges in AUD; the shop's other currencies remain estimates and the checkout says so.
- No Stripe Tax; GST and destination taxes are computed by the shop's existing `taxFor` and charged as shown.
- No membership, no CJ sourcing requests, no branded-product fulfilment.
- No legal review: the policy pages are drafts for a qualified person to check.

## Architecture

```
nexus/
  office/                          the Worker (TypeScript, Cloudflare Workers, wrangler)
    wrangler.toml                  name nexus-office, KV binding ORDERS, cron "0 */2 * * *", compatibility_date
    src/
      index.ts                     fetch router + scheduled handler; CORS; rate limit; JSON errors
      env.ts                       typed bindings and secrets
      catalogue.generated.ts       products the Worker may sell (generated by scripts/merge-office.mjs)
      pricing.ts                   quote(cart, country, methods, freight) → lines, shipping, tax, total (uses src/lib/shipping.ts, taxFor)
      cj.ts                        auth, freightCalculate, createOrderV2, confirmOrder, payBalance, getOrderDetail (shares radar/src/cj parsing shapes)
      stripe.ts                    create Checkout Session, verify webhook signature (Stripe SDK with fetch client + SubtleCrypto)
      orders.ts                    Order record, state machine, KV access, order numbers
      fulfil.ts                    paid → placed_with_supplier → shipped → delivered, needs_attention
      email.ts                     Resend: confirmation, shipped, needs-attention; no-op when disabled
      admin.ts                     token-protected merchant endpoints
      notify.ts                    "tell me when" list
    test/                          vitest (node) for pure modules; @cloudflare/vitest-pool-workers for handlers with KV
  scripts/merge-office.mjs         src/lib/data (+ listings) → office/src/catalogue.generated.ts
  src/lib/office.ts                shop-side client: enabled when VITE_OFFICE_URL is set
  src/pages/PoliciesPage.tsx       Terms, Privacy, Shipping & Returns, Contact
  src/content/policies/*.tsx       the policy text
  .github/workflows/office.yml     deploy the Worker on changes to office/ or the catalogue; set secrets
```

The shop keeps working with no Worker configured (the claude.ai artifact, local dev): `office.enabled === false` leaves today's prototype checkout in place, labelled "no payment taken". With `VITE_OFFICE_URL` set at build (from the repository variable `OFFICE_URL` in `pages.yml`), the real flow below is used.

## What is sellable

`sellable(product) = !!product.supplier`. `scripts/merge-office.mjs` writes `catalogue.generated.ts` with, for every product: `id, name, brand, category, price, variants[{id,label,delta}], fulfil, supplier, sellable`. The Worker refuses any line whose product is not sellable (`422 not_sellable`), so the rule is enforced where the money is, not only in the browser.

Shop: `ProductPage`, `QuickView`, `ProductCard` and the Advisor show `Add to cart` only for sellable products. Others show **Not yet stocked, tell me when**: an email field posting to `POST /notify {productId, email}`; a toast confirms. The compare, setup and guide pages are unchanged. When the Worker is not configured (prototype), every product stays addable so the artifact keeps demonstrating the checkout.

## Checkout

The shop's checkout keeps its sections: contact, delivery address, shipping, review. The card form is removed; the review section ends in **Pay with Stripe** (`Button primary`), with the note "Charged in AUD. Card, Apple Pay and Google Pay on Stripe's secure page." and links to the Terms and the Shipping & Returns policy.

`POST /checkout` body:

```json
{ "lines": [{ "productId": "cj-P-A1", "variantId": "cj-V-AU", "qty": 1 }], "email": "…", "address": { "name": "…", "line1": "…", "line2": "", "city": "…", "region": "…", "postcode": "…", "country": "AU", "phone": "…" }, "methods": { "CN": "standard" } }
```

The Worker:

1. Validates shape, email, country (must be in `COUNTRIES`), postcode (`validPostcode`), line quantities 1–10, products sellable, variants real. Any failure → `422 { error, field }`.
2. Prices every line from the catalogue (`price + variant.delta`), never from the client.
3. Freight for CJ lines: one `freightCalculate` per line (`startCountryCode 'CN'`, destination country and postcode, `vid`, quantity). The chosen line is the cheapest for `standard`, the fastest for `express` (same rule as `parseFreight`). USD → AUD at the Worker's rate (`fetchRate` logic: ECB via frankfurter, cached in KV for 24 h, fallback 1.52). Shipping charged = that line's AUD price, rounded up to .95 with a minimum of A$4.95 so freight never shows as odd cents. If CJ returns no line for a destination → `422 { error: 'no_freight', country }` and the shop says the item cannot ship there yet.
4. Tax via `taxFor(country, subtotal + shipping)`; added as a line when not included, shown as "Includes GST 10 %" in the product descriptions when included.
5. Writes `draft:<draftId>` to KV (TTL 24 h): lines with resolved prices, the freight line names per origin, address, email, totals.
6. Creates a Stripe Checkout Session: `mode 'payment'`, `currency 'aud'`, one `line_item` per product (`price_data.product_data.name`, `unit_amount` in cents, quantity), one for shipping, one for tax when applicable; `customer_email`; `client_reference_id: draftId`; `metadata { draftId }`; `success_url: SITE_URL + '#/orders/confirmed?session={CHECKOUT_SESSION_ID}'`; `cancel_url: SITE_URL + '#/checkout'`; `expires_at` 30 minutes.
7. Returns `{ url }`; the shop sets `location.href`.

The cart keeps showing the shop's lane estimates; the checkout's shipping step shows the real CJ quote once the address is known (`POST /freight` with the same validation, no draft written), so the number the customer sees before Stripe is the number charged.

## Orders

`Order` in KV at `order:<NX-id>`:

```ts
{ id: 'NX-123456', createdAt, email, address, lines: [{ productId, variantId, name, qty, unitPrice, vid, origin }],
  shipping: { origin: 'CN', method, logisticName, aud }, tax: { amount, included, label }, total, currency: 'AUD',
  stripe: { sessionId, paymentIntentId, paid: true },
  state: 'paid' | 'placed_with_supplier' | 'shipped' | 'delivered' | 'needs_attention' | 'refunded',
  supplier?: { cjOrderId, cjStatus, trackNumber?, logisticName?, placedAt, paidAt? },
  attention?: { reason, at, lastError }, history: [{ at, state, note }] }
```

Index keys: `session:<stripeSessionId> → NX-id` (idempotency), `open:<NX-id>` (orders the cron must poll), `email:<lowercase email>:<NX-id>` (lookup), `notify:<productId>:<sha256 of email>`.

Order numbers: `NX-` + six digits from `newOrderId` logic with a KV existence check.

`GET /orders/:id?email=` returns the order (email compared lowercase/trimmed) or `404`. `GET /orders/by-session/:sessionId` returns the order when the webhook has landed, else `202 { pending: true }`; the confirmation page polls it every 2 s for up to 60 s, then tells the customer the receipt from Stripe is their proof and the order will appear shortly.

## Fulfilment

`POST /stripe/webhook`: verify the signature with `STRIPE_WEBHOOK_SECRET`; on `checkout.session.completed` with `payment_status === 'paid'`: if `session:<id>` exists, return 200 (duplicate delivery); else load the draft, create the order (`state 'paid'`), write the indexes, then `fulfil(order)`; always return 200 to Stripe once the order is stored, even if fulfilment fails (the failure is recorded as needs_attention, not retried by Stripe).

`fulfil(order)` for CJ lines (one CJ order per shop order; all lines ship from CN in v1):

1. `createOrderV2` with `orderNumber: order.id`, `shippingCustomerName, shippingPhone, shippingAddress (line1), shippingAddress2 (line2), shippingCity, shippingProvince (region, or the city again for countries without regions, since CJ requires the field), shippingZip, shippingCountryCode, shippingCountry (name from COUNTRIES), email, fromCountryCode 'CN', logisticName: order.shipping.logisticName, remark: 'NEXUS', products: [{ vid, quantity }]` → `cjOrderId` from the reply's `data` (a string in CJ's examples; the client also accepts `data.orderId`).
2. `PATCH /shopping/order/confirmOrder { orderId }`.
3. `POST /shopping/pay/payBalance { orderId }` (CJ's docs also list `/shopping/payment/payBalance`; the client tries the first and falls back to the second on a 404). Skipped, with the state note `dry_run`, while the `CJ_DRY_RUN` var is `1`.
4. `state 'placed_with_supplier'`, `supplier.{cjOrderId, placedAt, paidAt}`; confirmation email (Nexus's own, with the order page link and the expected delivery window) when email is enabled.

Any step throwing → `state 'needs_attention'` with the reason (`cj_create_failed`, `cj_confirm_failed`, `cj_pay_failed: insufficient balance`, …) and the raw message; needs-attention email to Nick (`ADMIN_EMAIL`), always, even when customer email is disabled, because it goes to a plain address Resend's sandbox allows. The order stays in `open:`.

`scheduled` (cron every two hours): for each `open:` order with a `cjOrderId`, `getOrderDetail` → map CJ `orderStatus`: `SHIPPED` with `trackNumber` → `state 'shipped'`, store tracking and logistic name, shipped email with a 17track link; `DELIVERED` → `'delivered'`, remove from `open:`; `CANCELLED` → needs_attention. For `needs_attention` orders without a `cjOrderId`, the cron retries `fulfil` once a day (max 3 attempts) so a topped-up wallet clears the queue by itself.

## Merchant view

An **Orders** tab on the Radar page (`radar.html#orders`), gated by `ADMIN_TOKEN`: the page asks for the token once, keeps it in `localStorage['nexus.office.token']`, and sends `Authorization: Bearer`. Endpoints: `GET /admin/orders?state=` (newest first, 100 per page), `GET /admin/orders/:id`, `POST /admin/orders/:id/retry` (runs `fulfil` again), `POST /admin/orders/:id/refunded` (marks refunded after Nick refunds in Stripe; records the note), `GET /admin/notify` (counts per product with the emails), `GET /admin/health` (KV reachable, Stripe key mode, CJ auth ok, email enabled, last cron run). The view: a table of orders with state chips, the needs-attention queue first with the reason and the two buttons, and the notify list.

## Emails (Resend)

`email.ts` sends through `https://api.resend.com/emails` with `RESEND_API_KEY`; `FROM_EMAIL` (`orders@<domain>`) and `EMAIL_ENABLED` (`'1'` once the domain is verified) are Worker vars. Three plain-text-with-minimal-HTML templates: order confirmation (lines, totals, address, expected delivery, order link), shipped (carrier line, tracking number, 17track link), needs-attention (to `ADMIN_EMAIL`: order id, reason, link to the merchant view). When `EMAIL_ENABLED` is not `'1'`, customer emails are skipped and logged; the needs-attention email is still attempted. Failures to send never change an order's state.

## Policy pages

Routes `#/policies/terms`, `#/policies/privacy`, `#/policies/shipping-returns`, `#/policies/contact`, rendered by `PoliciesPage` from `src/content/policies/*.tsx` in the guides' reading style. Content, written plainly, dated, with a line that they are drafts pending professional review:

- Terms: who sells (Nexus Technologies Pty Ltd is a placeholder until the entity exists; the page reads the business name from one constant), prices in AUD including GST, order acceptance when Stripe confirms payment, delivery windows are estimates, Australian Consumer Law guarantees are not excluded, governing law NSW.
- Privacy: what is collected (name, address, email, phone, order contents), where it is held (Cloudflare KV in Nexus's account, Stripe for payment, CJdropshipping for shipping), browser storage for setup and cart, no advertising cookies, how to ask for deletion (email), retention 7 years for tax records.
- Shipping & Returns: routes and delivery windows per origin from `shipping.ts`; the returns rule exactly as decided; how to claim under ACL (contact, photos, outcome within 5 business days); who pays postage in each case.
- Contact: `CONTACT_EMAIL` constant (placeholder `hello@…` until the domain exists) and the ABN line (blank until it exists).

Footer links point at these routes; the "30-day returns on both routes" wording changes to "30-day change-of-mind returns on Australian stock; consumer guarantees on everything" in the cart, the home page and the footer. The checkout's Pay button carries "By paying you agree to the Terms and the Shipping & Returns policy".

## Security

- Prices, shipping and tax are computed server-side from the generated catalogue and the Worker's own CJ quotes; the client's numbers are never trusted.
- Stripe signature verified on every webhook; replay-safe through the `session:` index.
- CORS allows only `SITE_URL` (and `http://localhost:5173` when `DEV=1`); admin endpoints never set permissive CORS.
- Rate limits via KV counters with 60 s TTL: `/checkout` and `/freight` 20 per IP per minute, `/notify` 5 per IP per minute, `/orders/*` 60.
- Admin token compared in constant time; 401 without it; no token in URLs.
- Secrets exist only in Cloudflare and GitHub; `office/.dev.vars` is git-ignored; the catalogue module carries no secrets.
- Customer data: KV only; `GET /orders/:id` needs the matching email; the merchant view needs the token; logs never print addresses or emails.

## Error handling

- Every CJ call: 15 s timeout, one retry for network errors and 5xx; a `CjError` is stored verbatim in `attention.lastError`.
- Stripe session creation failure → `502 { error: 'stripe_unavailable' }`; the shop shows "Payment is unavailable right now; your cart is saved" and keeps the cart.
- Freight quote failure at `/freight` → the shipping step shows the shop's estimate with "final freight confirmed at payment"; at `/checkout` the quote is mandatory.
- Webhook with a missing draft (expired after 24 h, or a replay from another environment) → order created from the Stripe session's line items with `state 'needs_attention'` (`draft_missing`) so money is never taken without a record.
- Cron: each order isolated; one failure never stops the batch; `admin/health` reports the last run and its errors.

## Testing

- `pricing.test.ts`: lines priced from the catalogue, variant deltas, non-sellable refused, shipping rounding to .95 and the A$4.95 floor, tax included/added per country, quantity bounds.
- `cj.test.ts`: request bodies for createOrderV2/confirmOrder/payBalance from an order fixture (exact field names), freight line choice standard/express, getOrderDetail status mapping, tolerant parsing.
- `stripe.test.ts`: session payload (currency aud, cents, success/cancel URLs, metadata.draftId), signature verification with a known secret and a tampered body.
- `orders.test.ts`: state machine (allowed transitions only), order number uniqueness against a seeded KV, lookup by email case-insensitive.
- `fulfil.test.ts`: happy path, each failure step → needs_attention with the right reason, retry policy (max 3, once a day), idempotent webhook (second delivery is a no-op), draft missing path.
- `email.test.ts`: templates render the order; disabled mode skips customer mail but sends needs-attention; send failure does not change state.
- `handlers.test.ts` (workers pool): CORS, rate limit counters, `/orders/:id` with wrong email → 404, admin without token → 401.
- Shop: `app.test.tsx` cases for gating (branded product shows "tell me when"; CJ listing shows Add to cart), checkout calls `/checkout` and redirects, confirmation polling, policies routes render; Playwright scenarios with the Worker mocked via `page.route` for checkout, confirmation and the merchant view.
- Manual, before launch: a Stripe test-mode purchase end to end on the Pages site with the Worker in test keys and CJ in its real API but a `CJ_DRY_RUN=1` var that stops `payBalance` (orders created and confirmed, not paid) until Nick says go.
